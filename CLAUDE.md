# reevo-run

Budget-guarded LLM agents on a schedule, with a sandboxed tool executor and a
cloud-agnostic core behind swappable provider seams. See `README.md` for the
architecture and `CLEANROOM.md` for the clean-room rules that bind all work here.

## Database / Prisma — STRICT

PostgreSQL + Prisma 6. Migrations are the source of truth for the deployed
schema; `prisma/schema.prisma` is the declarative model. **The two must never
drift.** Follow these rules exactly — they are not optional.

### Hard rules

- **Never `prisma db push`.** It mutates a database without a migration and
  guarantees drift. There is no case for it in this repo.
- **Never modify an already-applied migration.** Deployed servers track
  migration checksums (`prisma migrate deploy`); editing an applied file breaks
  `migrate deploy` everywhere. Fix mistakes with a **new** additive migration.
- **Migrations are hand-written from the spec** (CLEANROOM.md rule 2) — never
  generated by diffing against another codebase, never copied. Write the SQL
  yourself under `prisma/migrations/<YYYYMMDD######>_<name>/migration.sql`.
- **Every schema change ships with its migration in the same change.** A PR that
  edits `schema.prisma` without the matching migration SQL (or vice-versa) is
  incomplete. This includes indexes and constraints: a `CREATE INDEX` in
  migration SQL **must** have a matching `@@index(...)` in `schema.prisma`, and
  a `@@index`/`@@unique` in the schema must have matching SQL. (A missing
  `@@index` is exactly the kind of silent drift this section exists to prevent.)
- **Prefer additive, reversible-in-practice migrations.** New nullable columns,
  new tables, new indexes. Avoid destructive changes unless the spec calls for
  them; when unavoidable, write them explicitly and deliberately.

### Required drift check (run after ANY schema or migration change)

The migration chain replayed onto an empty DB must produce **exactly** the
schema in `schema.prisma` — the diff must be empty. Verify it before committing:

```bash
npm run db:up                       # local Postgres on :55432 (docker compose)
docker exec local-postgres-1 psql -U reevo -d reevo \
  -c "DROP DATABASE IF EXISTS reevo_shadow;" -c "CREATE DATABASE reevo_shadow;"
npx prisma migrate diff \
  --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "postgresql://reevo:reevo@localhost:55432/reevo_shadow" \
  --script
docker exec local-postgres-1 psql -U reevo -d reevo -c "DROP DATABASE IF EXISTS reevo_shadow;"
```

**Clean = the output is `-- This is an empty migration.`** Any `CREATE`,
`ALTER`, `DROP`, or index statement means the schema and migrations disagree —
reconcile before committing (usually by adding the missing declaration to
`schema.prisma` so it matches the already-written SQL, or by writing the missing
migration). Also run `npx prisma validate`.

### Workflow

1. Edit `schema.prisma` to the target model.
2. Hand-write the additive migration SQL under
   `prisma/migrations/<YYYYMMDD######>_<name>/migration.sql`.
3. Apply locally: `npx prisma migrate resolve --applied <name>` against the
   local DB (or `npm run prisma:migrate` = `prisma migrate deploy`).
4. `npm run prisma:generate` (regenerate the client) after schema changes.
5. **Run the drift check above — it must be clean.**
6. `npm test && npm run build`.

Production applies migrations with `prisma migrate deploy` (`npm run
prisma:migrate`) — never `migrate dev`, never `db push`.
